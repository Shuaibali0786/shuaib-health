# API latency on the live API (T068), 2026-11-06

Read-only: 100 sequential GET requests in total (the agreed cap), no POST, no booking, no slots, from the owner's laptop with `backend/scripts/measure_latency.py` (about 16:57 UTC, 36 s in all). Target `https://shuaib-health-api.vercel.app`.

| Path | n | p50 | p95 | max | Status codes |
|---|---|---|---|---|---|
| `/health` | 30 | 286 ms | **558 ms** | 741 ms | 200 x30 |
| `/api/v1/clinic` | 25 | 266 ms | 284 ms | 313 ms | 200 x19, **403 x6** |
| `/api/v1/doctors` | 25 | 254 ms | 273 ms | 305 ms | **403 x25** |
| `/api/v1/lab-tests` | 20 | 252 ms | 264 ms | 296 ms | **403 x20** |

## Result: PARTIAL, catalog p95 NOT established
- `/health`: 30 good samples, p95 558 ms, under 1 s. **PASS** for that endpoint.
- Catalog: only the first 19 `/api/v1/clinic` requests returned 200 (those 19 were all under about 313 ms). **From the 20th request of the run on, every catalog request returned 403**, so the doctors and lab-tests timings are of the 403 responses, not of catalog work. They must **not** be read as catalog p95.
- Targets for SC-003 (p95 < 1 s) therefore remain **open for the catalog**.

## What the 403 is (not yet known)
- The application returns 403 only for a missing or wrong `X-Proxy-Secret` on booking writes and for admin rules (`backend/app/deps.py`, `errors.py`); the public catalog GET routes do not require the secret, and the app's own rate limiter answers 429, not 403.
- So the 403 most likely came from outside the app (a Vercel platform protection reacting to about 20 quick requests from one IP, or similar). **This is a hypothesis, not a finding.** It was not investigated further because the request budget was used up and the agent session has no Vercel team access.
- Why it matters: if a platform rule can block a single visitor after about 20 fast requests, it could also block a real visitor. The owner should look at Vercel -> `shuaib-health-api` -> Firewall / Observability for a denied-requests entry around 16:57 UTC on 6 Nov.
